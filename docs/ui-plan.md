# LLM 价格雷达 · UI 规划（依据 Joye 调研）

> 规划日期：2026-09-20
> 依据：`docs/joyehuang-blog-research.md`（合并版调研）
> 现状：单页静态工作台（模型价格 + 订阅计划 双 Tab），已具备：五维试算器、计费档位、星标关注、价格排序、CSV 导出、加载/空/错误/离线状态、明暗主题、键盘可达、响应式。
> 本规划把调研结论翻译成具体 UI 改造，按优先级排序。

---

## 0. 现状自评（先看我们踩中了什么）

| 调研原则 | 我们现状 | 差距 |
|---|---|---|
| 用层级而非边框套边框（#1） | **110 处 border**，卡片/表格/分区大量用边框 | 边框偏多，层级主要靠框线而非字号/明暗 |
| 结构化事件驱动 AI 界面（#3） | 五维试算器是结构化 parts 雏形，有缺价错误态 | 试算结果"可回放"、工具状态生命周期未做 |
| 内容即数据 / manifest（#7） | data.json / plans.json 干净，有 source 出处 | 无 content_hash / manifest / AI 检索入口 |
| 行为数据检验设计（#5） | 无埋点 | 星标/试算/导出是否真被用，无从得知 |
| 结果交付而非操作工具（#6） | 试算即算即出 | 未交代"将算什么/怎么算/结果是什么" |
| 响应式内容驱动断点（#2） | 固定 900px/560px 断点 | 未用 clamp()/Container Query/内容驱动断点 |

## 一、P0 — 信息层级重构（去掉边框套边框）

**目标**：让层级来自字号、字重、文字明暗和留白，边框只留给"并列单元 / 独立可点击卡片"。

**改动点：**

1. **详情面板重排**（当前 detail-head / rates-table / calc-block 都带边框 + 分隔线）
   - 建立三级字号：模型名标题（21–22px，现有 22px ✓）→ 档位表 / 试算字段（14.5px）→ 备注 / 提示（12px）
   - 表格去竖边框：档位表只留行分隔（hairline），去掉每格 border；用 `--fg-soft` 明暗表达主次
   - 备注区从"卡片 + 边框"改为"纯留白 + 左侧细线或背景 tint"（保留一种，不要又边框又背景）

2. **列表去重框**（当前 model-item 靠 hover 背景 + 分组边框）
   - 去掉 vgroup 之间的分隔 border，改用组间留白 + 组标题的字重/字母间距
   - 选中态用 `accent-soft` 背景 + 文字色，不再叠加边框

3. **状态色语义化**（峰值/空闲/促销/警告）
   - 峰值：当前 peak-pill 用红底红字 → 保留 pill（它是独立状态标签，合理），但详情内的"高峰 ×2"从彩色 pill 改为**文字 + 明暗**（用字号/字重表达，色彩仅辅助）
   - 促销/限期：从"黄底黄字"改为 **faint 文字 + 前缀符号**，减少彩色噪声

**验收**：详情区可读性提升；删除 >30% 的 border 声明；长文本/连续报错/空状态不拥挤。

---

## 二、P0 — 试算器升级为"可回放的结构化过程"

**目标**：把五维试算从"算完显示数字"升级为**结构化、可回放、带状态的记录**——这是调研 #3（UIMessage.parts）思想的最小落地。

**改动点：**

1. **试算结果 parts 化**
   - 每个成本项（普通输入 / 缓存读取 / 缓存写入 / 输出 / 缓存存储）是一个独立"part"，带自己的状态：`正常` / `缺价(未单列)` / `零`
   - 缺价项不再是整块报错，而是**该项就地标灰 + 说明**（"未单列，不代表免费"）
   - 预计费用 = 汇总 part，高亮但不盖过各项

2. **工具状态生命周期**（借鉴 `tool-${name}` part）
   - 档位选择：切换时短暂 `input-streaming`（微动效/读取中）→ `input-available`（已就绪）→ 输入即出 `output-available`
   - 缺价时 `output-error`（已部分实现），补上"该项就地的 error 态"

3. **试算历史（可选，P1）**
   - 最近 N 次试算存 localStorage，可"回放"（每次试算 = 一条结构化记录：模型 + 档位 + 输入 + 结果）
   - 这是 UIMessage 持久化思想的落地：试算过程可恢复，不只是最终数字

**验收**：切换档位 / 输入时有明确的进行中→就绪→结果反馈；缺价项就地可读；试算历史（若做）刷新后仍在。

## 三、P1 — 数据 manifest 化 + AI 可检索

**目标**：让价格雷达的数据像 joye 一样"内容即数据、可被 AI 增量同步"。

**改动点：**

1. **data.json / plans.json 补元数据**
   - 顶层加 `content_hash` + `updated_at`（models 已有 updated，补整体 hash）
   - 每个模型/计划已有 `source` 出处 ✓

2. **新增 `.well-known/llm-price-manifest.json`**（可选，或放项目根目录）
   - 结构参照 joye：`{ instructions, tree, endpoints, links }`
   - instructions：说明数据口径（官方命名、DeepSeek 高峰、缓存读写存含义）
   - endpoints：`/data.json`（模型）、`/plans.json`（订阅）
   - CORS 开放

3. **页面不依赖 manifest**（manifest 只是给外部/AI 的索引，页面仍读 data.json）

**验收**：拿到 manifest 的 AI/爬虫能理解数据口径并增量同步；页面行为不变。

---

## 四、P1 — 行为埋点（用数据检验设计）

**目标**：调研 #5——"PV 只证明来了，自定义事件才证明做了什么"。

**改动点：**

1. **localStorage 事件日志**（轻量，无后端）
   - 试算器：`calc_view`（曝光）/ `calc_result`（出了结果）/ `calc_error`（缺价）
   - 星标：`star_add` / `star_remove`
   - 导出：`export_click` / `export_done`
   - 订阅抽屉：`plan_open`

2. **简单的"使用概览"**（P1 末或 P2）
   - 一个极简面板/或仅 console 汇总：今天试算了几次、星标了几个、导出几次
   - 目标是**判断哪些功能真的被用**，不做复杂分析

**验收**：能在 localStorage 看到事件序列；能回答"试算器和导出有没有人用"。

---

## 五、P1 — 响应式升级（内容驱动断点）

**目标**：调研 #2——clamp() / Container Query / 内容驱动断点，而非只按设备名分页。

**改动点：**

1. 标题/价格用 `clamp()`（已在 masthead 用过，推广到 detail-head、sum 卡）
2. 列表与详情**各自**用 Container Query 适配（窄容器时详情内嵌计算器自动单列）
3. 断点从固定 900/560 改为**内容驱动**（如列表 320px、档位表列数到临界自动收起次要列——已有 col-ctx 思路）

**验收**：内容在中间宽度（如 700px）不突兀；详情内试算器随容器自适应。

---

## 六、P2 — 结果交付的文案（AI 界面观）

**目标**：调研 #6——页面交代"将做什么、正在做什么、结果是什么、哪里需要用户决定"。

**改动点：**

1. 试算器上方加一行"将算什么"说明（已有 cb-sub"按所选档位估算"，补全为：本模型按 X 档位，输入/读取/写入/输出互不重叠）
2. 缺价时不仅报错，还说明"哪里需要你核对"（官方计费说明链接）
3. 订阅计划的 promo 已带"请以下单页为准"✓，统一这种"边界说明"的文案风格

**验收**：首次使用的用户能理解试算口径，不用猜。

---

## 七、P2（可选亮点）— 终端模式

**目标**：把 joye 的伪文件系统当趣味亮点移植（差异化特色）。

**改动点：**

- 加一个"终端"视图（第三个 Tab 或角标入口）：`ls` 看厂商、`cat deepseek-flash` 看价格、`search flash` 搜索
- 纯前端实现（命令解析 + data.json 查询），无需后端
- 复用 Shiki 思路做高亮（或用简单等宽排版）

**验收**：能完整走一遍 `ls → cat <model> → search`；键盘友好。

> 说明：这是加分项，不影响主工作台。若用户不想要终端，可跳过。

---

## 八、P2（远期预留）— AI 助手架构

**目标**：调研 #3/#6——若未来加 AI 助手，用结构化事件流而非文本气泡。

**改动点（现在只留架构，不实现）：**

- 若加聊天式助手：直接采用 `UIMessage.parts` + SSE 事件流（text / tool / source 分部渲染）
- 可参考 AI Elements（shadcn/ui 的 AI 组件）
- 现在的五维试算器已经是 parts 雏形，未来可无缝接入

## 九、实施顺序建议

| 阶段 | 内容 | 预估 |
|---|---|---|
| **P0-1** | 信息层级重构（去边框、三级字号、状态色语义化） | 中 |
| **P0-2** | 试算器 parts 化 + 工具状态生命周期 | 中 |
| **P1-1** | 数据 manifest 化 + content_hash | 小 |
| **P1-2** | 行为埋点 + 使用概览 | 小 |
| **P1-3** | 响应式内容驱动断点 + clamp() | 小 |
| **P2-1** | 结果交付文案 | 小 |
| **P2-2** | 终端模式（可选亮点） | 中 |
| **P2-3** | AI 助手（预留架构，暂不实现） | 远期 |

**建议先做 P0-1 + P0-2**（直接提升现有工作台的质感与反馈），再做 P1 的埋点（小成本，之后能验证 P0 改动是否有效）。

---

## 十、风险与边界

- 信息层级重构是"减法"：删除边框后若留白/明暗没跟上，可能显空——需在真实内容下验收，不能只看设计稿。
- 埋点只存 localStorage，跨设备不共享；若将来要严肃分析需后端。
- manifest 若发布需注意 CORS 配置与 `content_hash` 计算口径一致。
- 终端模式是风格化功能，若偏离用户对"工作台"的预期，可随时下线。
