## 主要结论

最值得借鉴的内容集中在三个方向：**用排版建立信息层级，用结构化事件驱动 AI 界面，用真实行为数据检验设计**。纯视觉设计文章目前较少，但 Lab、Notes、博客和 Terminal 合起来，形成了从界面呈现到工程实现的参考材料。

另一个贯穿性的设计主张（本站最有特色的一点）：**把整站内容组织成"伪文件系统"（joye.devserver）**，让普通读者、命令行爱好者和 AI Agent 共用同一套内容目录——这是"Agent-first 内容架构"的完整落地示范。

## 一、设计与布局的直接收获

### 1.1 用层级控制注意力（信息层级 [1]）

作者在同一份任务数据上对比**三层边框、纯排版、背景分层**三种呈现。其原则是**用字号、字重、文字明暗和组间留白表达从属关系**；并列单元或独立可点击卡片仍可使用边框。观点来源注明为 Refactoring UI。

**示例参数：**

| 示例参数 | 原文取值 | 应用含义 |
|---|---|---|
| 字号 | 标题 21px / 步骤 14.5px / 日志 12px | 让任务、过程、细节有明显主次 |
| 文字 | ink / ink-soft 82% / muted / faint | 降低次要信息的视觉权重 |
| 浅色背景混合 | 步骤 7% / 日志 13% | 同一状态色表达嵌套深度 |
| 深色背景混合 | 步骤 12% / 日志 22% | 为暗色环境重新调整浓度 |

调研观察：桌面示例将三种方案并排，内容保持一致，便于直接比较。纯排版方案更轻，但部分浅灰日志较淡；这是视觉观察，未测量对比度。

**调研建议**：将这些数字作为试验起点，长文本、移动端和关键状态应重新检查可读性。

### 1.2 响应式布局的技术地图（前端实习指南 [2]）

| 技术 | 作者给出的主要场景 |
|---|---|
| Media Queries | 设备断点明确的页面 |
| 流式宽度与 max/min | 信息型内容页 |
| Flex / CSS Grid | 一维组件排列 / 二维复杂面板 |
| clamp() / Container Query | 组件化适配与设计系统 |
| Mobile first / 内容驱动断点 | 组合策略；避免只按设备名划分页面 |

文中同时列出圣杯、双飞翼布局及 Flex/Grid 的实现取舍，并强调 React Hooks、组件通信、渲染优化、虚拟列表、JavaScript 异步、TypeScript 和构建基础。

**可以立即采用的做法**：挑一块"任务 → 步骤 → 日志"界面，先删去重复内框，再统一标题层级、间距和状态色。用最长标题、连续报错和空状态试排；以内容开始拥挤的位置决定换列或折叠。关键成功与失败信息同时给出文字标识。

## 二、AI 界面与 Terminal 的交互架构

### 2.1 聊天界面应保留结构化过程（Message 类型 [3]）

作者区分 `UIMessage` 与 `ModelMessage`：**前者保存界面需要的 parts、metadata 和工具过程，后者用于模型输入**。建议持久化 `UIMessage`，调用模型时再转换；用工具 part 的状态表达输入生成、输入就绪、成功和失败。

原文涉及的链路为 `streamText → fullStream → toUIMessageStreamResponse → SSE → useChat → UIMessage.parts`。可借鉴的是**让事件与组件状态对应**，而不是让前端从自然语言猜执行进度。该笔记标注 AI SDK 6.x，落地时应对照项目安装版本。

**补充细节（调研深化）：**

- `fullStream` 是 AI SDK 内部统一后的**完整事件总线**，不只是文本：`text-start / text-delta / text-end / reasoning-delta / tool-call / tool-result / finish`。`textStream` 只是从这些事件里筛出纯文本增量的轻量视图。
- `tool-${name}` part 是 AI 聊天 UI 的关键设计点：能表达一个 tool call 的完整生命周期（`input-streaming → input-available → output-available → output-error`），比"assistant 发一句文本 + 前端猜进度"强很多。
- `UIMessage.parts` 可承载：`text`、`reasoning`、`tool-${name}`、`source-url`、`source-document`、`file`、`data-${name}`、`step-start`。
- **持久化优先存 `UIMessage` 而非 `ModelMessage`**：模型需要的消息 ≠ 产品需要保存的消息，两者混在一起会在工具调用、流式渲染、持久化时变混乱。
- 一句话理解："Vercel AI SDK 先把模型输出归一化成内部事件流，再通过 SSE Data Stream Protocol 增量发送到浏览器，前端按事件类型更新消息状态和 UI。"

**调研建议**：为文本、工具步骤、引用、附件分别建立渲染组件；明确等待、运行、失败、取消和完成的展示。持久化消息有利于恢复画面，但不能据此认定网络断线后能自动恢复服务端执行；**恢复执行需要单独设计**。

### 2.2 网站 Terminal 的价值在内容可访问性（manifest [7]）

manifest 实测返回 JSON，响应头允许跨域读取。目录用 `inline content` 或 `endpoint` 暴露内容，正文接口提供 markdown、html、headings、frontmatter、content_hash、updated_at；README 还注明终端内文章使用 **Shiki 高亮**。

**补充细节（调研深化）：**

- manifest 顶层字段：`version / name / site / description / instructions / tree / endpoints / links / generated_at`。
- 每个条目带 **`content_hash` + `updated_at`**：支持 Agent / 爬虫做增量同步，不用每次都全量拉取。
- 建议的 Agent 阅读路径：先读 `instructions` + `description` → 走 `tree` → 对 endpoint 条目 GET 取全文。
- 连"人格配置"都文件化了（`etc/personality.conf`：terminal-native、piano+cello、dry/low-key voice、zh-CN/en-AU/ts/py/rust）。

| 界面 | 读者或调用方 | 可借鉴的设计 |
|---|---|---|
| 网页与导航 | 普通读者 | 标题、摘要、分类、搜索和语言入口 |
| joye.devserver | 偏好命令行的读者 | ls / search / cd / cat 映射内容目录 |
| manifest 与正文 API | Agent 与内容索引 | 稳定入口、结构化元数据、增量更新字段 |

**调研建议**：让网页、终端和 API **共用内容模型**。同步时直接使用节点里的 `endpoint`，不从目录名拼地址（该站 FS 名称和真实文章 ID 可能不同）。Lab 未被 manifest 覆盖，说明发布新内容类型时应检查索引是否同步。

### 2.3 另一个 Terminal 案例：OpenHarness 的 TUI 架构 [9]

作者的源码阅读介绍了 **React/Ink 与 Node.js 负责 TUI、Python 负责 Agent 的双进程结构**，通过 stdin/stdout JSON-lines 通信；**Pydantic 定义消息契约**，事件涵盖文本增量、工具开始与结束、权限弹窗。这个案例说明**过程状态可以通过明确协议呈现**。

> 两者应区分：网页里的 joye.devserver 是内容浏览入口；OpenHarness 是作者分析的另一个项目，不能据此认定个人站终端也使用 Ink。

### 3.2 如何理解作者的技术选型（Next.js 选型 [4]）

Next.js 笔记源于一次 Grok 对话，倾向**轻量、可控的 Drizzle 与 Jotai**，同时保留 Prisma、Auth.js、Redux Toolkit 在团队工具链、完整认证、复杂状态上的位置。它提供的是**选择维度，没有给出统一条件下的性能实测**。

关键判断框架（三组"轻薄 vs 成熟"取舍）：

| 对比 | 倾向（新项目） | 何时选成熟方案 |
|---|---|---|
| Drizzle vs Prisma | Drizzle：轻薄 SQL-first、bundle 小、冷启动快、适 Serverless | 团队依赖成熟工具链、低 SQL 心智负担 |
| Arctic vs Auth.js | Arctic：可组合小零件、轻量 OAuth | 需要完整认证框架/严格能力 |
| Jotai vs Redux | Jotai：boilerplate 少、轻量优先 | 状态流转复杂、需严格规范 |

值得记的金句：
- "一旦部署环境对 bundle、冷启动、边缘兼容性特别敏感，ORM 的重量就会从'工程细节'变成'产品体验问题'。"
- "boilerplate = 为了使用框架不得不先写的一大堆样板结构，不是业务本身需要的代码。"
- "状态复杂度如果不高，就没必要过早引入一整套重型约束。"

**调研建议**：可以直接吸收"按需求比较"的框架，具体选型再记录依赖版本、部署环境、认证需求和团队能力。**尤其不要把"某 ORM 更快""Redux 不再适用"写成无条件结论**；示例 API 也不作为未经验证的生产代码。

## 四、用行为数据检验设计（流量分析 [5]）

### 4.1 五步分析框架

1. **时间序列**：找拐点再归因——"曲线本身没有信息量，拐点的归因才有"。7 月爆发用 GSC 翻案：搜索曝光峰值在 6 月（14,375 次），7 月回落到 9,591 且全月搜索点击仅 69 次——主引擎是微信/社区转发而非 Google。周粒度再看：访客 -34.6% 但 PV 仅 -4.7%，人均浏览 1.83→2.66，"流量在跌、读者质量在涨"。
2. **渠道结构**：警惕"无 referrer ≠ 直接访问"（微信/飞书/聊天内打开会抹掉来源，7 月 89.9% PV 无 referrer）。交叉验证：Vercel 标 1,187 个"Google 访客" vs GSC 真实搜索点击 69 次，差 17 倍（标签混入 Discover/News/Images）。
3. **内容矩阵**：单篇 vs 主题簇——Agent 面试主题 5 篇合计 7,000+ 访客占 70%+，Transformer 四部曲每篇 76–134 垫底。选题公式：**真实浏览量 + 自己真正做过的东西 + 命中搜索刚需**。
4. **转化漏斗**：**自定义事件才是行为真相，PV 只证明"来了"**。活动页 964 访客 91 人提交（近 10%）；首页弹窗 700 次交互 575 次关闭（82.1%），外链点击仅覆盖 4.1% 访客——"看起来在推广、实际在打扰"。
5. **受众画像**：Desktop 80.2%、Windows 58%、Chrome+Edge 78%；地区中国大陆 40.6%、美国 19.8%、日本 12%、新加坡 9.7%。注意解释边界（代理/网络污染地区、口径重叠不可简单相加）。

### 4.2 数据质量审计（六个坑）

404 无法归因原始 URL（内容迁移忘做 301 重定向，7 月 /404 有 420 次浏览，约 29% 来自搜索引擎）；标签口径混入非搜索来源；访客/页面/事件口径重叠；地区被代理污染；等等。

### 4.3 调研建议

给关键按钮和表单定义**曝光、开始、成功与放弃事件**，检查分母和去重规则。不能仅凭弹窗关闭率判定所有弹窗无效；应同时看任务完成率。终端未知命令只记类别，不收集自由输入。

## 六、从工具操作转向结果交付（AI 产品形态）

### 6.1 产品形态观点（分享会 [12]）

- **Agent 更像增量市场**（不是替代存量市场）。
- **交互会从"操作工具"走向"表达意图"**——用户不再点按钮操作对象，而是表达想要的结果。
- **普通开发者应深耕垂类上下文和工作流**（niche context + workflow）。
- 面试心态文章进一步提出：**模型行为和前端体验互相影响，模型错误可能需要 fallback UI**；80 分钟面试复盘强调完整的前后端、评估和可观测性。 [14][15]

**调研建议**：AI 页面同时交代"将做什么、正在做什么、结果是什么、哪里需要用户决定"。**权限边界由服务端验证，不能只靠隐藏按钮**；这与作者权限隔离文章对可信身份和请求作用域的讨论一致。 [17]

### 6.2 Agent 长期身份（补充来源 [A1]，2026-09-14 文章）

《给 Agent 一个邮箱：从工具到能一起做事的伙伴》提出 Agent 作为"长期同伴"的产品观：

- 邮箱 = 身份起点（Cloudflare Email Routing 转发、专属收件箱），但不只是"少介入"。
- **身份、记忆、任务状态、权限应由模型外的系统（Harness）保管**，不能寄托在一次模型调用里——"模型会换，会话会结束，服务会重启"。
- 好伙伴的标准：记得一起做过什么、知道自己有哪些工具账号资源、能接着推进没做完的事、有稳定表达但在证据面前会改。
- 设计启示：Agent 产品 = 可长期共事，不只是更快执行。

## 八、建议按以下顺序尝试

1. **先做一张任务详情页**：三层信息、统一状态、明暗主题。
2. **再接结构化流**：消息、工具步骤、引用和失败状态可回放。
3. **补内容入口**：网页、搜索、manifest 和稳定正文地址。
4. **最后验证**：检查桌面与移动端画面，记录关键动作与实际完成情况。

## 十、对我们（LLM 价格雷达）的具体应用建议

结合本项目现状（单页静态工作台：价格目录 + 订阅计划，数据来自 data.json / plans.json）：

1. **信息层级**：我们的详情/列表可用"标题→步骤→细节"的三层字号与状态色体系（信息层级 [1] 的参数可直接当起点），减少重复内框。
2. **结构化试算**：五维试算器的各成本项（普通输入/缓存读取/缓存写入/输出/存储）已是结构化 parts 的雏形——若将来做 AI 助手，直接采用 `UIMessage.parts` + SSE 事件流架构，不要退回单一字符串消息。
3. **manifest 化数据**：data.json / plans.json 已很干净，可加 `content_hash` / `updated_at`（models 已有 updated）；若要被 AI 检索，可参考 joye 的 `/.well-known/llm-price-manifest.json`（instructions + tree + endpoints + CORS）。
4. **行为埋点**：试算器、星标、导出是否真被用，值得埋"曝光/开始/成功/放弃"事件验证，避免"看起来在推广、实际在打扰"（首页弹窗 82% 关闭的教训）。
5. **前端选型**：当前纯静态单 HTML 符合 Joye"轻量优先、bundle 敏感"的判断；若升级框架，走 Drizzle/Jotai 轻量路线，勿上重型全家桶。
